# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

A working local prototype: LangChain + Ollama + pgvector in Docker, two command-line scripts, a FastAPI HTTP API over the same functions, a small document library (DMS: upload, indexing status, open/download, delete; `src/rag/dms/`), and a React frontend in `frontend/` (app shell with sidebar, session history, status card and theme switch; Chat, Documents and Ingestion screens; Release notes only places version-scoped questions in Chat). The API can also serve the built web app at `/` (`FRONTEND_DIST`, `src/rag/api/frontend.py`), so a server needs no Node.js. Not built yet: the 16.2 release-notes view, authentication, Azure providers, deployment, a relevance cut-off.

Branches:
- `integration`: the complete working application (backend + frontend). Create each new phase's branch from it (e.g. `feature/dms-api`), and merge the branch back after review and approval.
- `main`: lead-approved work only. It holds just the scaffold until the lead confirms requirements (VM, "16.2" product, mini DMS, hosting); `integration` is merged into it only then.
- `poc/langchain-ollama`, `feature/rest-api`, `feature/react-frontend`, `feature/ui-redesign`, `fix/rag-answer-quality`, `fix/sidebar-history-scroll`, `docs/refresh-guides`, `feature/dms` (the document library): earlier branches on GitHub, each contained in `integration`; kept for reference.
- Later branches were local only: each was fast-forwarded into `integration` after review and then deleted (serving the web app from the API, storage hardening, retrieval quality, hybrid search, 3 passages by default, the question log). Their commits are in `integration`'s history.

## Running the prototype (Windows, from the repo root)

```bash
python -m venv .venv                                              # Python 3.14 works
.venv/Scripts/python.exe -m pip install -e ".[ollama,pgvector,dev,api]"
cp .env.example .env                                              # defaults work as-is locally
docker compose up -d                                              # PostgreSQL 18 + pgvector on 127.0.0.1:5433
ollama pull gemma3:4b && ollama pull nomic-embed-text             # Ollama must be running
.venv/Scripts/python.exe scripts/ingest.py                        # index documents/ (re-run any time)
.venv/Scripts/python.exe scripts/ask.py "What is deprecated?" --version 16.2   # optional --product, --k
.venv/Scripts/python.exe -m uvicorn rag.api.app:app --host 127.0.0.1 --port 8000   # HTTP API; docs at /docs
cd frontend && npm install && npm run dev                         # web app on http://localhost:5173 (needs the API)
# Production-style instead: cd frontend && npm run build, then start uvicorn with FRONTEND_DIST=frontend/dist
#   and open http://127.0.0.1:8000 (the API serves the build; leave FRONTEND_DIST empty while using npm run dev)
```

- API endpoints (`src/rag/api/app.py`): `GET /health` (200 ok / 503 with `problems`), `POST /chat` (`{"question", "product"?, "version"?, "k"? 1–20, default 3}` → `answer`, `no_answer`, numbered `sources` with `excerpt`), `POST /documents/ingest` (no body; 202 + `job_id`, 409 if one is running), `GET /documents/ingest/{job_id}` (`running` / `succeeded` + `report` / `failed` + `error`; 404 if unknown). Document library (`src/rag/api/documents.py`): `POST /documents` (multipart `file`, `product`, `version`, `doc_type`; 201 + `ingest_job_id`, 409 path taken, 413 over `MAX_UPLOAD_MB`, 422 invalid), `GET /documents`, `GET /documents/{id}`, `GET /documents/{id}/file` (`?download=true`), `DELETE /documents/{id}` (204; 409 while a job runs; 500/503 with `file_deleted`/`chunks_deleted`/`record_deleted` if it stops part-way). Errors are `{"detail": "..."}`: 422 invalid input, 503 Ollama/database unavailable, 502 model call failed, 500 generic (details only in the server log). With `QUESTION_LOG` set, `/chat` appends one JSON line per question to that file (`src/rag/question_log.py`): question, filters, outcome, status, time, answer, and every passage the model was given (also for "I don't know", via `Answer.retrieved`), with `found_by` and `cited`; a write failure never fails the request, and a 500 logs only the exception's type.

- Put files at `documents/<product>/<version>/<doc_type>/<file>` (PDF, `.md`, `.txt`), e.g. `documents/documentum/16.2/release-notes/notes.pdf`; product/version/doc_type come from those folders. Re-running ingest skips unchanged files, replaces changed ones and removes deleted ones. Scanned PDFs (no text layer) are skipped.
- Passages per question default to 3 (`search.DEFAULT_K`, mirrored by `DEFAULT_TOP_K` in the frontend's `api/types.ts`): with the Documentum 23.4 documents, 3 instead of 5 cut answers from ~110 s to ~70 s with the same or better quality.
- On the 4-core laptop CPU, `gemma3:4b` takes ~20–65 s when a question needs new passages (mostly reading the prompt), a few seconds when the passages repeat, and 15–30 s more when the model has to load. `OLLAMA_KEEP_ALIVE_MINUTES` (default 30) keeps both models loaded between questions, holding ~5 GB of RAM.
- Tests: `pytest` (unit only, no services needed; API tests use FastAPI's `TestClient` with fakes) · `pytest -m integration` (needs Docker DB + Ollama; uses its own temporary tables and, for the API, a temporary documents folder) · single test: `pytest tests/unit/test_x.py::test_name`. Prefix with `.venv/Scripts/python.exe -m`. Add `-p no:warnings` to hide a harmless `langsmith` deprecation warning on Python 3.14. Frontend: `cd frontend && npm run typecheck && npm test && npm run build`.

## Layout and conventions

- src-layout package `rag` (`src/rag/`); import as `from rag.ingestion import ...`, never `from src...`. Flow: `ingestion/` (loaders → chunking → pipeline) → vector store → `retrieval/search.py` (vector search merged with `retrieval/keyword.py` full-text search + product/version filter) → `generation/` (prompt + LLM, `[n]` citations, fixed "I don't know" reply; `citations.py` repairs `[2], 4]`, drops citations of passages that don't exist and section numbers cited as passages (`[5.2.1.1]`), merges repeated citations; `answer()` removes the fixed reply when the model tacks it onto a real answer and turns citation-only or "not stated in the passages" replies into that reply, because `no_answer` and hidden sources depend on the exact text). Loaders drop PDF running headers/footers; chunking cuts all pages of a file as one text (`page` = page the chunk starts on) and prefixes each chunk with its numbered section headings (`Section: 2 About X > 2.1 New features`; heading detection in `chunking.is_heading()` is deliberately strict). Each chunk's `embedding_model` column holds `pipeline.index_fingerprint()` (model + `CHUNKING_VERSION` + chunk size/overlap): bump `CHUNKING_VERSION` when a loading/chunking change should rebuild existing chunks; the next ingest run then re-processes every file. Retrieval goes through `service.find_passages()`. With `HYBRID_SEARCH` (default on) `retrieve()` embeds the question once, runs the vector search and `keyword.keyword_search()` (own SQL, not `langchain-postgres`'s hybrid option: that ANDs every word, overwrites the distance and keeps the first question's words) with the same filters, `4 × k` each, and merges them with Reciprocal Rank Fusion (`fuse()`, `HYBRID_RRF_K`, default 10: with short lists the usual 60 never lets a keyword-only hit in); keyword hits carry their cosine distance from the same query, and every passage gets `found_by` (shown by `ask.py`). The keyword query ORs the question's `english` lexemes and scores each chunk by the BM25 IDF of the words it contains, so common words ("documentum") count for little. Then `choose()` keeps up to `PREFERRED_DOC_TYPE_SLOTS` of the `k` places for `PREFERRED_DOC_TYPE` (default `release-notes`) chunks within `PREFERRED_DOC_TYPE_MAX_GAP` of the best distance, so large guides don't crowd out release notes (`k` is still the number of passages returned, in fused order with hybrid search). Prompt wording was tuned against live `gemma3:4b` runs: re-check answers with the real model after changing it. Entry points: `scripts/ingest.py`, `scripts/ask.py` and the API (`src/rag/api/`). All of them go through `src/rag/service.py` (`build_services()`, `run_ingest()`, `find_passages()`, `ask()`, `sources_to_show()`); put shared glue there, not in a script or an endpoint.
- Keep third-party frameworks (e.g. LangChain) inside these modules behind our own functions (`ingest()`, `retrieve()`, `answer()`), so scripts, the API and tests don't depend on them. Unit tests use fakes (fake store, `FakeListChatModel`).
- API conventions: endpoints are plain `def` (FastAPI runs them in a thread pool; the vector store's sync calls rely on that), never `async def`. Services are built on first use, not at startup, so the server starts while Docker/Ollama are down. Backend exceptions are classified by `providers.unavailable_errors()` / `model_errors()`, so the API never imports Ollama/SQLAlchemy itself. Ingestion only ever reads `DOCUMENTS_DIR`, never a path from a request. Ingestion jobs live in memory (`api/jobs.py`, one lock, one job at a time), and the document library's status tracking (`dms/tracking.py`) relies on that: run exactly **one** uvicorn worker (never `--workers N`), and stop the old process completely before starting a new one (a second process would release and re-claim the first one's `processing` documents, and both would ingest at once). Job history is lost on restart.
- Document library (`src/rag/dms/`, endpoints in `api/documents.py`, screen in `frontend/src/features/library/`): uploads are stored in `DOCUMENTS_DIR` at `<product>/<version>/<doc_type>/<file>` (the layout ingestion reads), and recorded in a `documents` table linked to chunks only by `source`. `storage.py` owns every path: names are checked (`check_folder_name()`, `clean_filename()`), files are saved via a hidden `.uploads/` folder and `os.link` (never overwriting; `build_library()` removes temporary files abandoned there for over an hour), and `path_of()` refuses unsafe names (device names judged as Windows does), links and hard-linked files without using `resolve()`. Ingestion's `iter_files()` likewise never goes through a link inside `DOCUMENTS_DIR` and skips hard-linked files; if `DOCUMENTS_DIR` itself is missing or can't be listed it raises `DocumentsFolderUnreadable` (not an `OSError`, which the API would report as a service outage), so a run never empties the index by mistake. The frontend repeats the name and type rules in `validation.ts`: change both together. `tracking.py` wraps every ingestion job: it releases leftover `processing` rows, claims `pending`/`failed` ones, runs the unchanged `run_ingest()`, and updates only the rows it claimed; it also adopts files already in the folder where they are. The library reaches the `chunks` table only through `IndexAccess` (`dms/index.py`); it changes it only to delete one document's chunks. An upload starts a job when none runs and the services are up (`start_indexing_if_idle()` in `app.py`); a finished job starts a follow-up for documents still pending. `build_library()` runs on first use and is replaced by a fake in API unit tests.
- On this branch the `chunks` table is created by `providers.get_vector_store()` (no migrations); with `HYBRID_SEARCH` it also adds, if missing, the generated `content_tsv` column (`to_tsvector('english', content)`) and its GIN index (`keyword.ensure_text_search()`), also to an existing populated table (no re-ingest; needs the table owner). Changing `keyword.TEXT_SEARCH_CONFIG` needs that column dropped so it is rebuilt; `src/rag/database.py` holds the psycopg helpers (connections, URL conversion, `table_exists`, `indexed_files`, and for the library `chunk_counts`, `delete_chunks`). Don't add empty placeholder modules: create a module when it has code. Changing `METADATA_COLUMNS` or the embedding size needs the table dropped and documents re-ingested (`docker compose down -v` wipes the local DB).
- Dependencies are declared in `pyproject.toml` (there is no requirements.txt), with optional groups `ollama`, `pgvector`, `api` (FastAPI, uvicorn, python-multipart for uploads) and `dev` (pytest, httpx for `TestClient`). Don't use `langchain-community` (discontinued); load files with `pypdf` and plain Python into `langchain_core` `Document`s.
- Model backends and the vector store are built only in `src/rag/providers.py`; everything else uses LangChain's standard interfaces. Vector store = `langchain_postgres.PGVectorStore` (v2) on a table we define, with metadata as real columns (`METADATA_COLUMNS`) so filters are SQL; it connects via `asyncpg` (`async_database_url()`), never the deprecated `PGVector` class.
- Local database: `docker compose up -d` → PostgreSQL 18 + pgvector on `127.0.0.1:5433` (user/db `rag`). Always write `127.0.0.1`, not `localhost`, in database and Ollama URLs: on Windows `localhost` tries IPv6 `::1` first and stalls (database) or adds ~2 s per call (Ollama via urllib).
- Scripts (and the API's `/health`, `/chat` and `/documents/ingest`) run `rag.health.check_services()` first, so a stopped Docker/Ollama, a missing model or a bad `DATABASE_URL` ends with one clear line (or a 503) instead of a traceback.
- Config comes from `.env` via `rag.config.get_settings()`; `.env.example` lists the keys and defaults. `documents/` holds client files and is git-ignored.
